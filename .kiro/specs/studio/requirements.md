# Requirements Document

## Introduction

Studio is a web front end for the ComfyUI that this repo sets up on a Vast.ai Instance. The user picks a workflow and a model, uploads input images, adds LoRAs, adjusts settings, presses Generate, watches progress, and gets the images or videos back. Studio runs on the Instance beside ComfyUI, talks to ComfyUI only through the ComfyUI_API on 127.0.0.1:18188, and runs the UI-format graphs the repo already installs: the Converter turns each graph into API format, and a small committed Manifest says which node inputs each form control sets.

The first version covers krea2 (both graphs), qwen21, qwen21-edit, krea-style, edit-2509 and wan-i2v. minimax-h3 and wan-animate follow later with their own Manifests; the Manifest format already expresses their limits (Requirement 2).

**Relationship with the ai-influencer-pipeline.** That spec defines the Render_Template (`influencer-render-template/1`: a committed API graph with `{{name}}` placeholders and node ids below 900) and the Template_Filler in `scripts/influencer/templates.py`. The Filler is implemented and tested (its task 12); no Render_Template file is committed yet (its task 18). Studio shares the Filler instead of building a second one: the Job_Builder checks values with the Filler's placeholder types and inserts LoRA chains with the Filler's `lora_list` mechanism, and Studio reaches ComfyUI through the influencer's ComfyUI_Client. Studio does not store its workflows as Render_Templates, because a Render_Template commits a whole API graph while a Studio workflow is a graph the Instance installs, found through a Manifest; converted graphs also hold node ids such as `30:19` (nodes inside subgraphs) that the Render_Template rules refuse. The Render_Template format, its checks, the Filler's results and the influencer tests stay unchanged (Requirement 5).

**Changes to existing install commands** are proposals only, collected in Requirement 23 for the user's decision at review. Without them, Studio installs with its own new command and opens through an SSH tunnel. Facts that could not be verified from here are listed under Open items at the end.

Out of scope: a login of Studio's own (access control is Vast's Portal or an SSH tunnel), several users, Manifests for minimax-h3 and wan-animate, video or audio input slots, and editing graphs.

## Glossary

- **Studio**: the system specified here: Studio_Server, Frontend, Studio_Installer, Manifests and their tests.
- **Studio_Server**: the FastAPI application of Studio; it serves the Frontend and Studio's HTTP API, and is the only part of Studio that talks to the ComfyUI_API.
- **Frontend**: the static HTML, CSS and JavaScript files the Studio_Server serves; the Form, Progress_View, Gallery and History list are parts of the Frontend.
- **Studio_Service**: the supervisor program `studio` that runs the Studio_Server on the Instance.
- **Studio_Installer**: the new script `scripts/studio.sh` that installs, updates, restarts and reports on Studio.
- **Install_Lock**: the folder `Studio_Home/install.lock` that one `install` or `restart` at a time holds; it is made with `mkdir`, which either makes the folder or fails, also under the Mac's bash 3.2, and holds a file with the holder's process id and process start time.
- **Studio_Log**: `/var/log/portal/studio.log`, where supervisor writes the Studio_Server's standard output and standard error.
- **Tunnel_Command**: `ssh -p <port> root@<host> -L <Studio_Port>:127.0.0.1:<Studio_Port>`, the SSH command that forwards a local port of the user's machine to the Studio_Server; `<host>` and `<port>` are the Instance's SSH address (Requirement 21 criterion 16).
- **Studio_Home**: `/workspace/studio`, or the folder STUDIO_HOME names; it holds the Studio_Venv, the Studio_Data_Dir, the Conversion_Cache, the Install_Lock and the Studio_Installer's record of the last service start (Requirement 22 criterion 6).
- **Studio_Venv**: the Python virtual environment of the Studio_Server, `Studio_Home/venv`.
- **Studio_Requirements**: `config/studio/requirements.txt`, the Studio_Venv's package list: every package pinned with `==` and hashed for CPython 3.10 to 3.14 on Linux x86_64 and macOS arm64, kept as `tests/requirements-check.txt` is kept (the direct pins in its header, the rest generated from them).
- **Studio_Data_Dir**: `Studio_Home/data`: the History, the Presets, the Stored_Inputs and Studio's client_id (Requirement 5 criterion 10).
- **Studio_Port**: the loopback TCP port of the Studio_Server: 18190, or the port STUDIO_PORT names.
- **Instance**: a Vast.ai instance made from the stock ComfyUI template (REFERENCE.md §1).
- **Repo**: this git repository.
- **ComfyUI_API**: the HTTP and WebSocket API of the Instance's ComfyUI at COMFYUI_URL (default `http://127.0.0.1:18188`): /system_stats, /object_info, /upload/image, /prompt, /ws, /history, /view, /interrupt and /queue.
- **ComfyUI_Client**: `scripts/influencer/comfy.py` and `scripts/influencer/http.py`, the influencer pipeline's loopback-only client of the ComfyUI_API.
- **Converter**: the POST /workflow/convert endpoint that the node pack `SethRobinson/comfyui-workflow-to-api-converter-endpoint` adds to ComfyUI; GET /workflow/convert answers the Converter's name and version.
- **Workflows_Dir**: `/workspace/comfyui-user/default/workflows`, where the Repo installs workflow graphs.
- **Catalog**: `config/catalog.txt`; a **Catalog_Id** is a workflow id the Catalog lists.
- **Install_Name**: the name ComfyUI's loaders list for the file a `config/models.list` line installs: the line's file name, prefixed with the part of the line's subdir below its first folder and a `/` when that part is not empty (subdir `loras/Krea2` gives `Krea2/Krea2 NSFW+.safetensors`; an empty subdir gives the file name alone).
- **Providing_Id**: a Catalog_Id whose install provides a file name: an id in the `wf:` tag (or `global` for a line with no tag) of an active `config/models.list` line whose Install_Name equals the file name exactly, case and separators included.
- **UI_Graph**: a workflow file in ComfyUI's UI format (nodes and links, subgraph definitions included) in the Workflows_Dir.
- **Converted_Graph**: the API-format graph (node id → `class_type`, `inputs`, `_meta.title`) the Converter answers for a UI_Graph.
- **Conversion_Cache**: Studio's stored Converted_Graphs, in Studio_Home, keyed as Requirement 3 states.
- **Manifest**: a committed JSON file in `config/studio/manifests/` that makes one UI_Graph a Studio workflow.
- **Manifest_Loader**: the part of the Studio_Server that reads and checks Manifests.
- **Manifest_Printer**: the part of the Studio_Server that formats a Manifest as canonical JSON.
- **Node_Selector**: a Manifest entry naming one node of a Converted_Graph by title, class type or both, with an optional node id as fallback.
- **Binding**: a Node_Selector and an input name: one node input that a Manifest entry sets.
- **Control**: one Form field a Manifest declares (text, integer, float, choice, boolean, seed, size, frame count or model), with one or more Bindings that all take the Control's value, except that a size Control has one or more Bindings that take the width and one or more that take the height (Requirement 2 criterion 3).
- **Control_Limits**: the limits a Control's value has to meet: the Manifest's minimum, maximum, step, offset and maximum pixel count (Requirement 2 criterion 4); the minimum and maximum the current /object_info gives for each of the Control's Bindings (for a size Control, a width Binding's apply to the width and a height Binding's to the height); for a choice Control, the choices of Requirement 10 criterion 4; and, for a text Control, a length of at most 20,000 characters (Unicode code points). The step and round hints of /object_info are not Control_Limits.
- **Model_Picker**: a model Control, whose choices are the file names /object_info lists for the bound loader input.
- **Image_Slot**: a Form field for one input image, declared by a Manifest as required or optional.
- **Stored_Input**: an input image the Studio_Server keeps in the Studio_Data_Dir, byte for byte as the browser sent it, named by its SHA-256 and image type (Requirement 7 criterion 4); a Form_State names an Image_Slot's content by that hash.
- **Image_Loader**: a node that loads an Image_Slot's file, of the class LoadImage unless the Manifest names another class for the Image_Slot (Requirement 2 criterion 9).
- **Consumer_Input**: a node input that an Image_Slot names as taking the slot's image from a new Image_Loader node (Requirement 7 criterion 8).
- **LoRA_Target**: a Manifest entry naming a model loader output after which Studio chains the user's LoRAs.
- **Target_Output**: the node output a LoRA_Target names: the node its Node_Selector selects, at the output index the LoRA_Target gives.
- **LoRA_Stack**: the ordered list of LoRA_Entries the user sets for one LoRA_Target.
- **LoRA_Entry**: one LoRA file name, as /object_info lists the name (subfolder included), and a strength.
- **Chain_Loader**: a node the Job_Builder inserts for one LoRA_Entry, of the class LoraLoaderModelOnly unless the Manifest names another class for the LoRA_Target (Requirement 8 criterion 6).
- **Graph_LoRA**: a LoRA loader node the UI_Graph holds, which the Manifest lists with an optional switch Binding; an off Graph_LoRA's loader is removed from the prompt (Requirement 9 criterion 4).
- **Result_Node**: a node of the Converted_Graph whose saved files are a Job's results.
- **Output_Node**: a node whose class /object_info marks as an output node; ComfyUI validates and runs Output_Nodes and the nodes they depend on.
- **Form**: the Frontend view where the user sets a workflow's Controls, Image_Slots, LoRA_Stacks and Graph_LoRA switches, and presses Generate.
- **Form_State**: every value of the Form for one workflow: Control values, the seed and its randomize switch, Image_Slot contents (each by its Stored_Input's SHA-256), LoRA_Stacks and Graph_LoRA switches.
- **Valid_Form_State**: a Form_State of a Ready workflow that none of the Form_State refusals listed in Requirement 13 criterion 1 refuses.
- **Generate request**: the request the Frontend sends the Studio_Server when the user presses Generate; it names the workflow and holds its Form_State and a request id (Requirement 13 criterion 9).
- **Job**: one press of Generate: a Form_State, the prompt built from the Form_State, the prompt's ComfyUI prompt_id (the Job id), its Job_State and its result files.
- **Job_State**: one of Queued, Running, Succeeded, Failed, Cancelled and Lost.
- **Job_Builder**: the part of the Studio_Server that turns a Manifest, a Converted_Graph and a Form_State into a Job's API prompt.
- **Studio_Core**: the parts of the Studio_Server that hold Studio's logic apart from its HTTP routes and Live_Sockets: the Manifest_Loader, the Manifest_Printer, the Job_Builder, the storage of Studio_Home's files and the calls to the ComfyUI_API.
- **Ready**: the state of a workflow that no readiness check fails, decided as Requirement 4 criterion 7 states; a readiness check is any check of these requirements that marks a workflow not Ready.
- **Progress_View**: the Frontend view of a Job's progress.
- **Live_State**: the progress the Studio_Server holds for each Queued and Running Job: the Job_State; for a Queued Job, its queue position; for a Running Job, the executing node's Node_Label, the step count, the cached-node count, the elapsed time and the newest preview. A Job leaves the Live_State when it ends, with a last change that carries its final Job_State and run time.
- **Live_Socket**: the WebSocket connection that each browser tab or window showing the Frontend holds to the Studio_Server, over which the Studio_Server sends the Live_State and its changes.
- **Gallery**: the Frontend view of the Jobs' result files.
- **History**: Studio's records of every Job (one **History record** per Job), kept in the Studio_Data_Dir.
- **History_Version**: the whole-number format version every History record holds, starting at 1; each Studio_Server version writes exactly one History_Version, and a higher number is newer.
- **Preset**: a named, saved Form_State of one workflow, without Image_Slot contents.
- **Node_Label**: how Studio names a node of a Job's prompt to the user. A node of the Converted_Graph: the `_meta.title`, class type and id the prompt holds for it (a node inside a subgraph keeps its whole id, such as `30:19`). A node the Job_Builder inserted: its class type and the Form item it serves, never its Studio-made id (a Chain_Loader by its LoRA_Entry's file name, the label of its LoRA_Target and the entry's position counted from 1; an Image_Loader by its Image_Slot's label). Any other node id: as ComfyUI sends it.
- **Plain_Error**: a message in plain English that names the workflow, the node concerned by its Node_Label, the file or value concerned, and the next step.
- **Template_Filler**: `check_values` and `fill` in `scripts/influencer/templates.py` (ai-influencer-pipeline design §A3).
- **Render_Template**: the influencer pipeline's template format `influencer-render-template/1` (ai-influencer-pipeline design §C7, §M6).
- **Setup_Script**: `scripts/stock-setup.sh`.
- **First_Boot_Script**: `scripts/vast-provision.sh`.
- **Provisioner**: `scripts/provision.sh`, the install engine that `finish`, `all` and each `stock-setup.sh <id>` run.
- **Check_Suite**: `scripts/check.sh` and the tests it runs.
- **Selection_Snapshot**: `tests/fixtures/selection-v6.txt`, the ai-influencer-pipeline's record of what the Provisioner selects at v6 for each v6 Catalog_Id, for `global` and for a full run; `tests/phase1/test_provision_bash.py` fails when the current configuration selects anything else for those runs.
- **Fake_ComfyUI**: the test double of the ComfyUI_API in `tests/fakes/comfy.py`.
- **Portal**: Vast's Instance Portal: the Caddy reverse proxy with token authentication that PORTAL_CONFIG and `/etc/portal.yaml` configure.
- **Reference_Doc**: `REFERENCE.md`. **Changelog**: `CHANGELOG.md`.

## Requirements

### Requirement 1: Workflow discovery

**User Story:** As the user, I want the workflow picker to list only the workflows installed on this Instance, with their Catalog description, so that every workflow I pick can run.

#### Acceptance Criteria

1. THE Studio_Server SHALL offer one workflow for each Manifest that the Manifest_Loader accepts and whose UI_Graph file exists, whether or not ComfyUI answers at COMFYUI_URL, and no workflow for any other Manifest. The Manifests are the files directly in `config/studio/manifests/` whose names end in `.json`; a UI_Graph file exists when the Workflows_Dir itself, not a subfolder, holds a regular file whose name equals the Manifest's UI_Graph file name exactly, case included.
2. THE Form SHALL show each offered workflow in the workflow picker with the Manifest's label and the description field of the Catalog line for the Manifest's Catalog_Id, ordered by the position of that line in the Catalog and, among Manifests of one Catalog_Id, by Manifest name in byte order.
3. WHEN the Frontend requests the workflow list, which the Frontend does when its page loads and when the user presses the Form's refresh button (Requirement 6 criterion 4), THE Studio_Server SHALL read the Manifests, the Catalog, the Workflows_Dir and /object_info again and run, for each offered workflow, every readiness check (Glossary: Ready; Requirement 4 criterion 7 lists them) before answering, so that installs, removals and fixes show without a restart of the Studio_Service.
4. THE Form SHALL show in the workflow picker, as the Studio_Server's latest answer to the workflow list gives them, whether each offered workflow is Ready together with every reason a workflow is not Ready, and, as entries that cannot be picked, the file name and the Manifest_Loader's message (Requirement 2 criterion 6) of every Manifest the Manifest_Loader rejects.
5. THE Studio_Server and THE Frontend SHALL hold no code that depends on a particular Catalog_Id, Manifest name or graph file name, so that a Manifest whose Catalog_Id, name and UI_Graph file name occur in no Studio_Server or Frontend source file is offered, checked and built like a first-version Manifest, and a new workflow needs only its Manifest, with no change to Studio_Server or Frontend files.
6. THE Repo SHALL hold exactly one Manifest for each first-version graph, naming the graph by the file name `config/models.list` installs and giving the graph's Catalog_Id: `image_krea2_turbo_t2i.json` and `simpleKrea2NSFWLLM_v10.json` (krea2), `image_qwen_image_2_1_t2i.json` (qwen21), `image_qwen_image_2_1_image_edit.json` (qwen21-edit), `image_krea2_turbo_int8_image_style_reference.json` (krea-style), `image_qwen_image_edit_2509.json` (edit-2509), and the graph file that `uncensoredWan22Remix_v10.zip` extracts (wan-i2v; its name is to be read on an Instance, Open item 7).
7. IF ComfyUI answers none of the calls a readiness decision makes (Requirement 4 criterion 7: /system_stats, GET /workflow/convert and /object_info, each getting no connection or no answer within the ComfyUI_Client's time limit for the call, 10 s for /system_stats and GET /workflow/convert and 30 s for /object_info), THEN THE Studio_Server SHALL mark every offered workflow not Ready with one reason only: a Plain_Error saying that ComfyUI does not answer at COMFYUI_URL, with the command `bash scripts/stock-setup.sh restart`.
8. WHILE the Studio_Server's latest answer about the workflow of the open Form gives the workflow as not Ready or no longer offered, THE Form SHALL disable Generate and show every reason from that answer beside Generate.
9. IF a Generate request names a workflow that criterion 1 does not offer, or that is not Ready, when the Studio_Server receives the request, THEN THE Studio_Server SHALL record no Job, upload no image to ComfyUI and submit no prompt, and answer every reason, stating for a workflow no longer offered whether its Manifest is gone, its Manifest is rejected or its UI_Graph file is missing from the Workflows_Dir, the last with a pointer to the Reference_Doc's reinstall steps.

### Requirement 2: Manifest format

**User Story:** As the maintainer, I want each supported graph described by a small committed Manifest, so that adding a workflow means adding one file.

#### Acceptance Criteria

1. THE Manifest_Loader SHALL accept a Manifest only when the file is one JSON object holding exactly these keys, each present even when its list is empty: the format id `studio-manifest/1`; a name equal to the file name without `.json`, of 1 to 64 characters from a–z, 0–9, `-` and `_`, starting with a letter or digit; a label; a Catalog_Id the Catalog lists; a UI_Graph file name that ends in `.json` after at least one other character, is at most 255 bytes in UTF-8 and holds no `/`, `\` or control character (U+0000 to U+001F and U+007F), whether or not that file exists (Requirement 1 criterion 1); a list of one or more Result_Nodes and a list of nodes to remove, each entry a Node_Selector; and lists of Controls, Image_Slots, LoRA_Targets and Graph_LoRAs.
2. THE Manifest_Loader SHALL accept Node_Selectors that hold a title, a class type or both, each a non-empty string, plus an optional node id: a string of whole numbers without leading zeros joined by `:` (such as `7` or `30:19`); and Bindings that hold a Node_Selector and a non-empty input name.
3. THE Manifest_Loader SHALL accept the Control kinds text, integer, float, choice, boolean, seed, size (a width and height pair), frame count and model, each Control with an id, a kind, a label, one or more Bindings (for a size Control, one or more Bindings of the width and one or more of the height), and an optional default: a string for text and choice, a non-empty string for model, true or false for boolean, an integer for integer and frame count, an integer from 0 to 18446744073709551615 for seed, an integer or finite float for float, and an integer width and height for size.
4. THE Manifest_Loader SHALL accept, for integer, float, size and frame count Controls, an optional minimum, maximum, step and offset (integers, or integers and finite floats for a float Control; an offset only together with a step, 0 when absent), under which a value is valid when the value is an integer (for a float Control, an integer or a finite float), lies within the given minimum and maximum, both included, and, where a step is given, differs from the offset by a whole multiple of the step, computed exactly on each number's shortest decimal form (the fewest digits that read back as the same number; so with step 0.01, 0.07 is valid and 0.075 is not); for a size Control, these limits apply to the width and to the height separately, and an optional maximum pixel count, an integer from 1, bounds width × height.
5. THE Manifest_Loader SHALL accept a Manifest that states MiniMax H3's limits: a frame rate Control, integer or float, with minimum and maximum 24, so that 24 is its only valid value; a frame count Control with step 17 and offset 5 (17n + 5), so that 5, 22 and 107 are valid and 21 is not; and a size Control with step 32 and a maximum pixel count of 1032192 (768 × 1344), so that 768 × 1344 and 1344 × 768 are valid, 784 × 1344 breaks the step and 1024 × 1024 breaks the pixel count.
6. IF a Manifest breaks a rule of this requirement, each rule checked from the file and the Catalog alone (for example: a file that is not UTF-8 JSON text, NaN, Infinity and escaped unpaired surrogates included; a key given twice in one object; a missing key, an unknown key, or a key the entry's kind does not take; a value of the wrong type, length or characters; a Node_Selector with neither a title nor a class type; a minimum above its maximum; a step of 0 or less; an offset without a step; a default outside the Control's limits; or a duplicate that criterion 11 forbids), THEN THE Manifest_Loader SHALL reject that Manifest alone (it makes no workflow, and every other Manifest loads as if the file were absent), with one message, shown in the Form's workflow list and written to the Studio_Server's log, that names the Manifest file and lists every broken rule, each with its key path where the rule concerns a key (keys joined by `.`, list positions counted from 1 in square brackets, as in `a.b[2].c`).
7. THE Manifest_Printer SHALL format a Manifest as canonical JSON in the form of ai-influencer-pipeline design §A2: UTF-8 without a byte order mark; the keys of every object in ascending Unicode code point order; no white space outside strings; characters beyond ASCII written as themselves, with only `"`, `\` and U+0000 to U+001F escaped; integers exactly in decimal; and floats in their shortest decimal form; so that equal Manifests (criterion 8) always print to identical bytes.
8. FOR ALL valid Manifests, parsing, printing with the Manifest_Printer and parsing again SHALL give an equal Manifest: the same keys and values at every level, lists in the same order, and every number of the same kind (integer or float) and value (round trip).
9. THE Manifest_Loader SHALL accept Image_Slots, each with an id, a label, whether the slot is required (true or false), an optional Image_Loader class given together with the name of its file input (LoadImage and `image` when absent), and exactly one of a Node_Selector of the slot's existing Image_Loader node or one or more Bindings of the Consumer_Inputs a new Image_Loader node links to (Requirement 7 criteria 8 and 9).
10. THE Manifest_Loader SHALL accept LoRA_Targets, each with an id, a label, a Node_Selector of the model loader, the index of the loader output (an integer from 0) and an optional Chain_Loader class given together with three different input names for the model, the file name and the strength (Requirement 8 criterion 6); and Graph_LoRAs, each with an id, a label, a Node_Selector of the loader node and an optional switch: a Binding and the switch input's off value, true or false, whose opposite is the on value (Requirement 9 criteria 2 and 3).
11. THE Manifest_Loader SHALL accept a Manifest only when every list in it holds at most 64 entries; every label is 1 to 80 characters, not all white space; every Control, Image_Slot, LoRA_Target and Graph_LoRA holds an id of 1 to 64 characters from a–z, 0–9 and `_` that no other of these entries holds; no two Bindings hold equal Node_Selectors and the same input name; and no node to remove has a Node_Selector equal to another Node_Selector of the Manifest, where two Node_Selectors are equal when each of the title, the class type and the node id is absent from both or the same in both.

### Requirement 3: Graph conversion and caching

**User Story:** As the user, I want Studio to run the graphs the repo installs, converted once and reused until they change, so that Studio needs no second copy of any graph.

#### Acceptance Criteria

1. WHEN the Studio_Server needs a UI_Graph's Converted_Graph (to decide a workflow's readiness, to open a workflow's Form or to build a Job) and the Conversion_Cache holds no entry for the UI_Graph's current key, or holds one that does not read back in the shape criterion 6 requires, THE Studio_Server SHALL send the Converter the bytes of the UI_Graph file whose SHA-256 the key holds, unchanged, and store an answer that passes the checks of criterion 6 under that key in place of every entry the Conversion_Cache holds for that UI_Graph file name, so that the Conversion_Cache holds at most one entry per UI_Graph file name.
2. THE Studio_Server SHALL key each Conversion_Cache entry by four parts, taken as they stand at each need of criterion 1 (the UI_Graph's current key): the SHA-256 of the UI_Graph file; the Converter version GET /workflow/convert reports; the ComfyUI version /system_stats reports; and the SHA-256 of the whole /object_info entries, choice lists included, of the node classes the UI_Graph and its subgraphs use, where a class /object_info does not list counts as absent, so that installing the class changes the key.
3. WHILE a UI_Graph's current key equals the key of a Conversion_Cache entry that reads back in the shape criterion 6 requires, THE Studio_Server SHALL use that entry's Converted_Graph without sending POST /workflow/convert, also after the Studio_Service restarts.
4. WHEN the Studio_Server builds a Job, THE Studio_Server SHALL build the Job's prompt only from the Converted_Graph of the UI_Graph's current key taken at that moment, converting again first where a key part changed since the workflow's Form opened (for example a node pack installed and ComfyUI restarted), and submitting nothing where that Converted_Graph cannot be had (criteria 5, 6, 9 and 10).
5. IF ComfyUI answers GET /workflow/convert, but not with HTTP 200 and a JSON object holding a non-empty Converter name and version (for example with HTTP 404), THEN THE Studio_Server SHALL mark every workflow not Ready, keeping every Conversion_Cache entry but using none, with a Plain_Error saying that the Instance's ComfyUI lacks the Converter, naming the HTTP status received and pointing to the Converter fix in the Reference_Doc (Requirement 25 criterion 1).
6. IF POST /workflow/convert gets no connection, no answer within 30 s, an HTTP status other than 200, or an answer other than a JSON object of one or more nodes that each hold a `class_type` string and an `inputs` object, THEN THE Studio_Server SHALL mark every workflow whose Manifest names the UI_Graph not Ready, changing nothing in the Conversion_Cache, with a Plain_Error naming the UI_Graph file and the failure: no connection, the 30 s limit, or the HTTP status with the Converter's error text (the answer's `error` text where it holds one, else at most the answer's first 200 characters), plus the file's size in bytes for HTTP 413, the Converter's answer to a body over 1 MB.
7. THE Studio_Server SHALL read UI_Graph files without creating, changing, moving or deleting any file in the Workflows_Dir.
8. FOR ALL Converted_Graphs of the shape criterion 6 requires, storing a Conversion_Cache entry and reading the entry back SHALL give an equal Converted_Graph: the same JSON value, with every integer of any size (18446744073709551615 included) read back as the same integer and every decimal as the same decimal (round trip).
9. IF a UI_Graph file cannot be read, is not valid JSON, or is not a JSON object holding a list of nodes as ComfyUI's UI format does, THEN THE Studio_Server SHALL mark every workflow whose Manifest names the file not Ready, sending nothing to the Converter and changing nothing in the Conversion_Cache, with a Plain_Error naming the file and the cause and, for a JSON syntax error, its line and column.
10. IF /system_stats, GET /workflow/convert or /object_info gets no connection or no answer within its time limit (10 s for /system_stats and GET /workflow/convert, 30 s for /object_info), or /system_stats or /object_info gives an answer the ComfyUI_Client refuses, THEN THE Studio_Server SHALL mark every workflow not Ready, with the one reason Requirement 1 criterion 7 gives where ComfyUI answers none of these calls (ComfyUI does not answer at COMFYUI_URL at all) and otherwise with a Plain_Error naming the call and the failure, keeping every Conversion_Cache entry, so that at the first need after ComfyUI answers again an entry whose key has not changed is used without a new conversion (criterion 3).
11. WHILE a POST /workflow/convert for a UI_Graph's current key awaits its answer, THE Studio_Server SHALL serve every need of criterion 1 for that UI_Graph and key that arises meanwhile from that one conversion's outcome (its Converted_Graph, or the Plain_Error of criterion 6), sending no second POST /workflow/convert.

### Requirement 4: Node selection and readiness

**User Story:** As the maintainer, I want Manifests to find nodes by title or class type, with the node id only as a fallback, so that Manifests survive graph edits that renumber nodes.

#### Acceptance Criteria

1. WHEN the Studio_Server resolves a Node_Selector (which holds a title, a class type or both; Requirement 2 criteria 2 and 6 reject any other), THE Studio_Server SHALL select the node of the Converted_Graph, nodes inside subgraphs (ids such as `30:19`) included, that is the only node matching the selector, whatever node id the selector holds; a node matches when its `_meta.title` equals the selector's title where the selector gives one, compared case-sensitively after removing leading and trailing whitespace from both, and its `class_type` equals the selector's class type exactly where the selector gives one, and a node without a string `_meta.title` matches no selector that gives a title.
2. ### Requirement 11: Seed and reproducibility

**User Story:** As the user, I want to fix or randomize the seed and rerun past settings exactly, so that I can reproduce an image.

#### Acceptance Criteria

1. WHERE a Manifest declares a seed Control, THE Form SHALL show the seed Control's field with a randomize switch beside it.
2. WHEN the Studio_Server accepts a Generate request (Requirement 13 criterion 1) whose randomize switch is on, THE Studio_Server SHALL draw the Job's seed from a cryptographically secure random source, uniformly over the seed range of criterion 7.
3. WHEN the Studio_Server accepts a Generate request whose randomize switch is off, THE Studio_Server SHALL take as the Job's seed the value the request's Form_State holds for the seed Control.
4. THE Progress_View SHALL show with each Job the seed the Job used, as the exact integer of criterion 7 (the History list and the Gallery show it as Requirement 17 criterion 2 and Requirement 16 criterion 2 state).
5. THE Job_Builder SHALL set every Binding of the seed Control to the Job's seed, as a JSON integer.
6. THE Repo SHALL hold first-version Manifests whose seed Control binds every seed input of the graph's Converted_Graph fixture on a node the Manifest does not list for removal: each INT input named `seed` or `noise_seed`, and each other INT input that the graph's /object_info fixture marks with `control_after_generate`, those of prompt-refinement nodes included (for example TextGenerate in the Krea 2 Turbo graph and AdvPromptEnhancer in the Simple Krea2 NSFW+ LLM graph).
7. THE Studio SHALL carry seeds as exact integers, with no rounding in the Form, Studio's HTTP API, the History, the Presets or the submitted prompt, within the seed range: from the highest of 0 and every minimum the current /object_info gives for the seed Control's Bindings, to the lowest of 18446744073709551615 and every maximum it gives for them (18446744073709551615 for KSampler).
8. FOR ALL Converted_Graph fixtures, Valid_Form_States, Job seeds and Job ids, building the prompt twice from the same Manifest, Converted_Graph, /object_info, Form_State, Job seed and Job id SHALL give equal prompts: the same JSON value, with every number of the same kind (integer or float) and value (determinism property).
9. WHEN the user loads a History record into the Form (Requirement 17 criterion 3), THE Form SHALL set the seed Control's field to the seed the Job used, not to the field value the record's Form_State holds, and turn the randomize switch off.
10. IF the Manifest (compared by the SHA-256 of its canonical JSON), the UI_Graph file (by its SHA-256), the Converter's name or version, or the ComfyUI version differs from what a loaded History record holds, or the record holds none for one of them (Requirement 17 criterion 8), THEN THE Form SHALL name each such item with the record's value and the current value, because the same settings can then give a different prompt or image.
11. THE Manifest_Loader SHALL accept a Manifest only when it declares at most one seed Control, rejecting a Manifest with more as Requirement 2 criterion 6 states (with the key path of each further seed Control), so that a Form holds at most one seed and one randomize switch.
12. WHERE a Manifest declares no seed Control, THE Frontend SHALL show no seed field and no randomize switch in the workflow's Form, and no seed with the workflow's Jobs.
13. WHERE a Manifest declares no seed Control, THE Studio_Server SHALL count no seed and no randomize switch among the workflow's Form_State fields (Requirement 12 criterion 8), draw no seed, and record the workflow's Jobs without a seed.
14. WHILE the seed field holds text other than one or more digits 0–9 with no sign, decimal point, exponent, white space or leading zero ("0" itself excepted), or a number outside the seed range of criterion 7, THE Form SHALL mark the seed field with the rule broken (for the range, with its bounds), keep the text as typed and keep Generate disabled, whether the randomize switch is on or off (this makes Requirement 10 criterion 5 precise for the seed Control).
15. IF a Generate request holds for the seed Control a value other than a JSON string of the form of criterion 14, or a number outside the seed range of criterion 7, THEN THE Studio_Server SHALL record no Job, upload no image and submit nothing, whether the randomize switch is on or off, and answer the Control's id, the value and the rule broken, in one answer with the refusals of Requirement 5 criterion 9 and Requirement 10 criterion 6.
16. THE Frontend and Studio's HTTP API SHALL carry every seed (the seed field's value and prefill, each Job's seed, and the seeds of History records and Presets) as a JSON string of decimal digits, because a JavaScript number cannot hold every integer above 9007199254740991 exactly.
17. WHEN the Studio_Server answers a Generate request, THE Form SHALL keep the seed field's value and the randomize switch as the user set them, so that with the switch on each drawn seed shows only with its Job (criterion 4).
18. THE Studio_Server SHALL give each Job exactly one seed whatever its batch size: a Job whose batch size Control is above 1 takes that seed on every seed Binding (criterion 5), and its History record, the History list and the Gallery give that one seed for every result file of the Job.
19. WHEN a Job is built from a History record loaded into the Form with every value loaded (Requirement 17 criterion 4 refusing none) and none changed, while the Manifest, the UI_Graph file, the Converter's name and version, the ComfyUI version and /object_info equal those of the earlier Job, THE Job_Builder SHALL build a prompt equal to the earlier Job's submitted prompt except for the Result_Nodes' `filename_prefix` inputs (Requirement 12 criterion 4). Studio promises equal prompts, not equal pixels: GPU kernels need not be deterministic, and ComfyUI may serve unchanged nodes from its own cache.

### Requirement 12: Job building

**User Story:** As the maintainer, I want the Job_Builder to change a graph only where the Manifest says, so that Studio runs the graph the repo installs.

#### Acceptance Criteria

1. THE Studio_Server SHALL build every prompt it submits only from the Manifest the Generate request names, the Converted_Graph of that Manifest's UI_Graph for the current Conversion_Cache key (Requirement 3 criteria 3 and 4), the current /object_info, the request's Form_State, the Job's seed (Requirement 11 criteria 2 and 3) and the Job id, taking no graph, node id, class type or input name from the browser.
2. WHEN a Job is built, THE Job_Builder SHALL remove from the prompt every node the Manifest lists for removal, each found by its Node_Selector (Requirement 4 criteria 1 and 2), for example the ImageCompare node of qwen21-edit.
3. IF an input of a node the Manifest does not list for removal links to a node the Manifest lists for removal and is neither a Binding nor a Consumer_Input, or a node the Manifest lists for removal is also selected by a Binding, Image_Slot, LoRA_Target, Graph_LoRA or Result_Node of the Manifest, THEN THE Studio_Server SHALL mark the workflow not Ready with a Plain_Error naming the listed node and either the linking node and input or the other Manifest entry.
4. WHEN a Job is built, THE Job_Builder SHALL set the `filename_prefix` input of every Result_Node to the string `studio/<Manifest name>/<Job id>`, replacing any value or link the input held.
5. WHEN a Job is built, THE Job_Builder SHALL keep every Converted_Graph node that criterion 2, Requirement 7 criterion 9 and Requirement 9 criterion 4 do not remove, including nodes that no Output_Node depends on after those removals. Each kept node SHALL keep its Converted_Graph id, and every key and input (`class_type` and `_meta` included) SHALL match the Converted_Graph in JSON type and value: an integer stays an integer, a float stays a float so `1.0` is not sent as `1`, a string keeps every character, and a link keeps its node id and output index. The only exceptions are the inputs changed by criterion 4 (filename prefixes), Requirement 7 criteria 8 and 9 (Image_Slots), Requirement 8 criterion 5 (LoRA chains), Requirement 9 criteria 3 and 4 (Graph_LoRAs), and Requirement 10 criterion 7 and Requirement 11 criterion 5 (Bindings). The submitted prompt therefore carries each kept node's `_meta` to ComfyUI (frame property).
6. FOR ALL Converted_Graph fixtures and Valid_Form_States, THE Job_Builder SHALL build a prompt in which each Binding whose node the prompt keeps holds a value, not a link. That value SHALL be: the Job's seed on every seed Binding (Requirement 11 criterion 5); a size Control's width and height on its width and height Bindings; the Manifest's on or off value on a Graph_LoRA's switch Binding, as the Form_State's switch gives (Requirement 9 criterion 3); and the Form_State's value on every other Binding (binding property).
7. FOR ALL Converted_Graph fixtures and Valid_Form_States, THE Job_Builder SHALL build a prompt that meets all of these conditions (graph property):
   - it is acyclic
   - it holds none of the nodes that criterion 2, Requirement 7 criterion 9 and Requirement 9 criterion 4 remove
   - it holds only node classes that /object_info lists
   - every link (an input value `[node id, output index]`) names a node of the prompt and an output index from 0 to one less than the number of outputs /object_info lists for that node's class
8. IF a Generate request has any of the problems below, THEN THE Studio_Server SHALL build nothing, submit nothing, create no Job and answer with every problem found: the Manifest name, each reason the workflow is not Ready, each unknown or missing field and each empty required Image_Slot.
   - It names a Manifest that the Studio_Server does not offer (Requirement 1 criterion 1).
   - It names a Manifest whose workflow is not Ready when the request arrives.
   - It holds a field other than that workflow's Form_State fields (one per Control, Image_Slot, LoRA_Target and Graph_LoRA of the Manifest, plus the seed's randomize switch).
   - It lacks one of those fields.
   - It leaves a required Image_Slot empty.
9. WHEN a Job is built, THE Job_Builder SHALL build the prompt from a copy of the Converted_Graph, leaving the Converted_Graph and its Conversion_Cache entry unchanged, and SHALL apply these steps in this order, each to the previous step's result:
   1. removal of the nodes the Manifest lists (criterion 2)
   2. LoRA chain insertion (Requirement 8 criterion 5)
   3. Graph_LoRA switching and bypass (Requirement 9 criteria 3 and 4)
   4. Image_Slot wiring (Requirement 7 criteria 8 and 9)
   5. Control values, the Job's seed included (Requirement 10 criterion 7, Requirement 11 criterion 5)
   6. Result_Node filename prefixes (criterion 4)

   As a result, an input that took an off Graph_LoRA's output, where that Graph_LoRA took a Target_Output, ends linked to the LoRA_Target's last Chain_Loader, or to the Target_Output when the LoRA_Stack is empty.
10. IF a Result_Node's class is not an Output_Node, or has no input named `filename_prefix` of type STRING in /object_info (PreviewImage, for example, has none), or the Result_Node's `filename_prefix` input is also a Binding of the Manifest, THEN THE Studio_Server SHALL mark the workflow not Ready with a Plain_Error naming the Result_Node's title, class type and id and the failed check.

### Requirement 13: Submitting, queueing and cancelling Jobs

**User Story:** As the user, I want to press Generate, queue several Jobs and cancel any of them, so that I control what the GPU works on.

#### Acceptance Criteria

1. WHEN the Studio_Server accepts a Generate request, THE Studio_Server SHALL record the Job as Queued, upload the Job's input images (Requirement 7 criterion 7) and submit the built prompt with POST /prompt, a new lowercase UUID4 as prompt_id, Studio's client_id (Requirement 5 criterion 10) and `extra_data` holding `preview_method` set to `auto` (a ComfyUI release without `extra_data.preview_method` sends no previews, Open item 5). The Studio_Server accepts a Generate request whose request id has no Job yet (criterion 10) when none of these refusals applies:
   - the Form_State refusals: Requirement 1 criterion 9, Requirement 4 criterion 8, Requirement 5 criterion 9, Requirement 7 criterion 14, Requirement 8 criterion 10, Requirement 9 criterion 8, Requirement 10 criterion 6, Requirement 11 criterion 15, Requirement 12 criterion 8 and Requirement 15 criterion 3
   - the request refusals: criteria 11 and 21 of this requirement
2. WHILE earlier Jobs are Queued or Running, THE Studio_Server SHALL accept further Generate requests as criterion 1 states, up to the limit of criterion 21, and track each Job's Job_State separately.
3. WHEN the user cancels a Job recorded as Queued after the Studio_Server has sent the Job's POST /prompt, THE Studio_Server SHALL, once that POST /prompt is answered or the lookup of criterion 13 has ended, send POST /queue with `delete` naming the Job's prompt_id, then read the Job's state as criterion 6 states, recording the Job as Cancelled, not Lost, where neither GET /queue nor GET /history lists the prompt_id, and cancelling the Job as criterion 4 states where GET /queue lists it as running (a Job that has ended by then is answered as criterion 16 states).
4. WHEN the user cancels a Job recorded as Running, THE Studio_Server SHALL read GET /queue and, only where that answer lists the Job's prompt_id as running, send POST /interrupt naming the prompt_id right after that answer, with no other request of the cancel between the two (an older ComfyUI release may ignore the prompt_id and interrupt whatever runs, Open item 10), and SHALL record the Job as Cancelled once ComfyUI reports the prompt interrupted (an `execution_interrupted` message for the prompt_id, or a GET /history entry read as criterion 6 states).
5. IF the GET /queue answer of criterion 4 does not list the Job's prompt_id as running, THEN THE Studio_Server SHALL send no POST /interrupt and SHALL record the Job's state as criterion 6 states from that answer and a GET /history read that follows it.
6. WHEN the Studio_Server reads a Job's state from ComfyUI (at the Studio_Server's start for every Job the History records as Queued or Running with a submitted prompt, and wherever these requirements cite this criterion), THE Studio_Server SHALL read GET /queue first and then GET /history, change no Job where either read gets no answer in full, and otherwise record the first of these that applies:
   - GET /history holds the Job's prompt_id: the outcome the entry gives, with the result files of Requirement 16 criterion 1: Succeeded for success, Cancelled for interrupted, and Failed for error or an entry that gives no outcome, with the Plain_Error of Requirement 15 criterion 4
   - GET /queue lists the prompt_id as running: Running
   - GET /queue lists the prompt_id as pending: Queued
   - neither lists the prompt_id: Lost, with a Plain_Error saying that ComfyUI has no record of the Job, as after a ComfyUI restart
7. WHILE the Studio_Server's latest answer to the Frontend gives ComfyUI as not answering at COMFYUI_URL (the reason of Requirement 1 criterion 7), THE Frontend SHALL disable Generate and every Cancel control and show that reason with its command `bash scripts/stock-setup.sh restart`.
8. THE Form SHALL disable Generate while any of Requirement 1 criterion 8, Requirement 4 criterion 9, Requirement 6 criterion 3, Requirement 7 criterion 10, Requirement 8 criterion 9, Requirement 9 criterion 7, Requirement 10 criterion 5, Requirement 11 criterion 14 and criteria 7 and 9 of this requirement applies, and SHALL enable Generate while none applies.
9. WHEN the user presses Generate, THE Form SHALL send one Generate request holding a new request id, a lowercase UUID4 made in the browser, and keep Generate disabled until the Studio_Server answers that request or the browser reports the request failed, so that a double-click sends one request.
10. THE Studio_Server SHALL record at most one Job per request id, also for requests with one request id that arrive together or on either side of a Studio_Server restart (the Job's History record keeps its request id), and SHALL answer a Generate request whose request id already has a Job with that Job's id and Job_State, recording, uploading and submitting nothing.
11. IF a Generate request holds no request id, or one that is not a lowercase UUID, THEN THE Studio_Server SHALL record no Job, upload and submit nothing, and answer that the request id is missing or malformed.
12. WHEN ComfyUI answers a Job's POST /prompt with HTTP 200 and a JSON object whose prompt_id is the Job's, THE Studio_Server SHALL track the Job (Requirement 14 criterion 4), also where the answer's `node_errors` is not empty (Requirement 15 criterion 9 reports those node errors).
13. IF a Job's POST /prompt gets no connection, no answer within 30 s, or an answer other than HTTP 400 (Requirement 15 criterion 1) and the answer of criterion 12 (another status, a body that is not a JSON object, or a 200 answer naming another prompt_id or none), THEN THE Studio_Server SHALL send no second POST /prompt for the Job, read GET /queue and then GET /history every 2 s for up to 30 s, track the Job as criterion 6 states as soon as either lists the Job's prompt_id, and record the Job as Failed with the Plain_Error of Requirement 15 criterion 10 where neither has listed it when the 30 s end.
14. THE Studio_Server SHALL write the built prompt into the Job's History record before sending the Job's POST /prompt, so that a record without a prompt names a Job that ComfyUI never received.
15. IF a Job that the History records as Queued holds no submitted prompt when the Studio_Server starts, THEN THE Studio_Server SHALL record the Job as Failed without asking ComfyUI about it, with a Plain_Error saying that Studio stopped before submitting the Job and that loading its History record and pressing Generate runs it again.
16. IF the user cancels a Job that has ended (Succeeded, Failed, Cancelled or Lost), THEN THE Studio_Server SHALL change nothing, send ComfyUI nothing, and answer with the Job's final Job_State.
17. WHEN the user cancels a Job recorded as Queued before the Studio_Server has sent the Job's POST /prompt, THE Studio_Server SHALL send no POST /prompt for the Job and record the Job as Cancelled.
18. IF a request that a cancel sends ComfyUI (GET /queue, POST /queue with `delete` or POST /interrupt) gets no connection or no answer within the ComfyUI_Client's time limit for the call, THEN THE Studio_Server SHALL send no further request for that cancel, keep the Job's Job_State, and answer that the cancel failed, with the Plain_Error of Requirement 1 criterion 7, which the Frontend shows beside the Job.
19. THE Studio_Server SHALL send POST /queue with `delete` and POST /interrupt only for the prompt_id of a Job the Studio_Server submitted, and only to carry out the user's cancel of that Job.
20. IF, within 30 s of sending a Job's POST /interrupt, the Studio_Server has received no `execution_interrupted` message for the Job's prompt_id and read no GET /history entry of the Job, THEN THE Studio_Server SHALL read the Job's state as criterion 6 states and, where the Job is still Running, send the Frontend a Plain_Error, shown beside the Job, saying that the cancel did not take effect.
21. IF a Generate request arrives while 20 Jobs are Queued, THEN THE Studio_Server SHALL record no Job, upload and submit nothing, and answer that at most 20 Jobs can be Queued at once.

### Requirement 14: Progress and previews

**User Story:** As the user, I want to watch a Job's progress and previews live, so that I know how far the Job is and can cancel early.

#### Acceptance Criteria

1. WHILE a Job is Queued, THE Progress_View SHALL show the Job's position in ComfyUI's queue: 1 plus the number of pending prompts from any client that GET /queue lists with a lower queue number than the Job's (Requirement 5 criterion 3). The position SHALL update within 3 s of each change in ComfyUI's queue.
2. WHILE a Job is Running, THE Progress_View SHALL show: the Node_Label of the node named by the latest `executing` message for the Job; the step count as "step value of max", taken from the latest `progress` or `progress_state` values for that node, with no step count for a node that has sent none; "n of m nodes cached" when `execution_cached` listed n > 0 of the submitted prompt's m nodes; a notice that no preview has arrived, shown until the first one arrives; and the elapsed time in whole seconds since the Studio_Server recorded the Job as Running, counted on the Studio_Server's clock and updated at least once per second.
3. WHEN a tab's Live_Socket delivers a preview of a Running Job, THE Progress_View SHALL show that preview in place of the Job's previous preview or no-preview notice, and SHALL keep it until a newer preview arrives or the Job ends.
4. WHILE the /ws connection to ComfyUI is open, THE Studio_Server SHALL update the Live_State of each Queued and Running Job from two sources: the /ws messages that carry the Job's prompt_id (`execution_start`, `execution_cached`, `executing`, `progress`, `progress_state`, `executed`, `execution_success`, `execution_error`, `execution_interrupted`), and binary preview frames of type 1 (image type, then image) and type 4 (JSON metadata, then image). A frame belongs to the Job that is Running when it arrives, unless its metadata names another prompt_id. THE Studio_Server SHALL record a Queued Job as Running at the first message that carries its prompt_id. After `execution_success`, `execution_error` or `execution_interrupted`, it SHALL read GET /queue and then GET /history and record the Job's state as Requirement 13 criterion 6 states, reading both again at most 1 s apart while GET /queue still lists the prompt. It SHALL ignore every other /ws message and binary frame, including every message about a prompt Studio did not submit.
5. THE Studio_Server SHALL send each Live_State change to every open Live_Socket within 1 s of receiving the /ws message, GET /queue answer or GET /history answer that causes the change. The bound SHALL hold for up to 8 open Live_Sockets, and while one of them reads nothing. Previews that criterion 10 drops are exempt. The Check_Suite SHALL measure the bound on one monotonic clock, from the Fake_ComfyUI sending each scripted /ws message (Requirement 26 criteria 5 and 6) to a test client's Live_Socket receiving the resulting change, or, where the user does not approve Requirement 23 P-6, to the Studio_Core handing the change to the Live_Sockets (Requirement 26 criterion 13).
6. IF the /ws connection to ComfyUI closes or cannot be opened, THEN THE Studio_Server SHALL try to reconnect with the client_id of Requirement 5 criterion 10: first within 2 s, then 2 s after each failed attempt, with no limit on attempts. Every 2 s until a connection is open, and once more right after it opens, it SHALL run a round: read GET /queue, then GET /history, and record each Queued and Running Job's state as Requirement 13 criterion 6 states, where a Job whose prompt_id GET /queue lists as running becomes Running. A round that ComfyUI does not answer in full SHALL change no Job, and a round SHALL leave unchanged any Job submitted after the round's GET /queue read began.
7. WHEN a Job ends (the Studio_Server records it as Succeeded, Failed, Cancelled or Lost), including a Job for which ComfyUI sent no `executing` or `progress` message (as when every node is cached), THE Progress_View SHALL show the Job's final Job_State and run time. The run time is the whole seconds between the Running and final timestamps of the Job's History record (Requirement 17 criterion 1). A Job that is Lost, or that the Studio_Server never recorded as Running, SHALL show no run time.
8. THE Studio_Server SHALL push the Live_State to the Frontend over one Live_Socket per open tab. Each Live_Socket SHALL begin with the whole current Live_State, after which the Studio_Server SHALL send every later change to every open Live_Socket, so that all open tabs show the same progress, and SHALL replay no change made before that Live_Socket opened. THE Studio_Server SHALL refuse a Live_Socket handshake that Requirement 20 criterion 3 or 4 refuses.
9. IF a tab's Live_Socket closes, THEN THE Frontend SHALL show that live updates are paused and SHALL try to reopen the Live_Socket 2 s after the close and 2 s after each failed attempt, with no limit on attempts. Once the Live_Socket reopens, THE Frontend SHALL replace what the tab shows with the Live_State the Studio_Server sends first (criterion 8). For each Job the tab showed as Queued or Running that the Live_State no longer holds, it SHALL show the final Job_State and run time of criterion 7.
10. THE Studio_Server SHALL leave at least 250 ms between two previews it sends on one Live_Socket, and SHALL always send the newest preview it holds for the Running Job. It SHALL drop, unsent: every preview superseded by a newer one before it is sent on that Live_Socket; every preview larger than 1 MB (1,048,576 bytes); every preview frame that belongs to no Running Job (for example, a type-1 frame that arrives while no Job is Running); and every frame whose image is neither JPEG nor PNG.

### Requirement 15: Error reporting

**User Story:** As the user, I want plain error messages that name the node or model file at fault, so that I know what to fix.

#### Acceptance Criteria

1. IF ComfyUI answers a Job's POST /prompt with HTTP 400, whatever the answer's body, THEN THE Studio_Server SHALL record the Job as Failed with a Plain_Error holding ComfyUI's error (the `type`, `message` and `details` of the answer's `error` object, or else the answer in the ComfyUI_Client's `answer_excerpt` form: the answer's `error` text where it holds one, otherwise at most its first 200 characters) and each node error as criterion 7 states.
2. IF a node error of type `value_not_in_list` (criteria 1 and 9), or a finding of criterion 3, concerns a file input (a Model_Picker's Binding, a Chain_Loader's file name input, a Graph_LoRA loader's `lora_name` input, or another input whose value equals the Install_Name of an active `config/models.list` line), THEN THE Studio_Server SHALL say in the Plain_Error that the file is not installed, calling it a LoRA file where the node is a Chain_Loader or a Graph_LoRA's loader and a model file otherwise, name the file and the node's Node_Label, and give the next step as Requirement 6 criterion 6 states (each Providing_Id of the file name, the Manifest's Catalog_Id first where it is one, or that no install of the Repo provides the file).
3. IF an input of the built prompt that an Output_Node depends on holds a value outside the choices the current /object_info lists for the input, the image inputs Requirement 7 criterion 8 sets excepted, THEN THE Studio_Server SHALL record no Job, upload no image and submit nothing, and answer, for each such input, a Plain_Error naming the value (the file name, for a file input of criterion 2), the node's Node_Label and the input.
4. IF a Job's GET /history entry gives the outcome error or no outcome (Requirement 13 criterion 6), THEN THE Studio_Server SHALL record the Job as Failed with a Plain_Error naming, from the entry's `execution_error`, the Node_Label of the node it names, ComfyUI's exception type and ComfyUI's exception message, or, where the entry holds no `execution_error`, saying that ComfyUI reported the Job failed without naming a node or an exception.
5. THE Studio_Server SHALL keep in the Job's History record each Plain_Error of the Job and ComfyUI's full error answer: the whole body of a POST /prompt answer that refused the prompt or reported node errors, or the whole `execution_error` message of the Job's GET /history entry, traceback included.
6. THE Frontend SHALL show each Plain_Error beside the Job, field or control concerned (beside Generate for a refused Generate request), with ComfyUI's full error answer (criterion 5) behind a details control.
7. THE Studio_Server SHALL give in a Plain_Error, for each node error ComfyUI sends (the `node_errors` of an HTTP 400 or 200 answer to POST /prompt), the node's Node_Label, the Node_Label of each output node the node error's `dependent_outputs` lists and, for each of the node's errors, the input name, the received value, and ComfyUI's message and details.
8. IF the HTTP 400 answer of criterion 1 holds no node error (`node_errors` absent or empty), THEN THE Studio_Server SHALL say in the Plain_Error that ComfyUI refused the prompt as a whole without naming a node, with the next step: pressing the Form's refresh button, which decides again whether the workflow is Ready (Requirement 4 criterion 7).
9. WHEN ComfyUI answers a Job's POST /prompt with HTTP 200 and a non-empty `node_errors` (Requirement 13 criterion 12), THE Studio_Server SHALL record with the Job a Plain_Error saying that ComfyUI queued the Job without the output nodes these node errors block, and giving each node error as criterion 7 states, while the Job stays tracked.
10. WHEN the Studio_Server records a Job as Failed under Requirement 13 criterion 13, THE Studio_Server SHALL say in the Plain_Error how POST /prompt failed (no connection; no answer within 30 s; the HTTP status with the answer in the `answer_excerpt` form of criterion 1; a 200 answer whose body is not a JSON object; or a 200 answer naming another prompt_id, or none, in place of the Job's), that neither GET /queue nor GET /history listed the Job's prompt_id within 30 s, and that Studio did not submit the Job again.
11. IF a Job's `execution_error` reports the GPU out of memory (an exception type ending in `OutOfMemoryError`, or an exception message holding "out of memory", ignoring letter case), THEN THE Studio_Server SHALL add to the Plain_Error of criterion 4 the next step: a smaller size or batch size, or fewer LoRA_Entries.
12. THE Studio_Server SHALL quote in a Plain_Error at most the first 2,000 characters (Unicode code points) of each text ComfyUI sends (an error or exception message, or its details), marking a shortened text as shortened, and leave the full text and the traceback to ComfyUI's full error answer (criteria 5 and 6).
13. WHEN a Job or a refused request has more than one Plain_Error, THE Studio_Server SHALL give each distinct Plain_Error once and in a fixed order: first those from ComfyUI's answer, the node errors in the order of the answer's `node_errors` keys, then Studio's own, in the order of the requirement and criterion that raises each and, within one criterion, in the order of the Manifest entries concerned.
14. THE Frontend SHALL show every text that comes from ComfyUI or from a graph (error and exception messages, tracebacks, node titles and file names) as plain text, interpreting no part of the text as HTML.

### Requirement 16: Results gallery and downloads

**User Story:** As the user, I want the images and videos of my Jobs in a gallery with downloads, so that I get my results off the Instance.

#### Acceptance Criteria

1. WHEN a Job ends as Succeeded, Failed or Cancelled, THE Studio_Server SHALL record the Job's result files in its History record. These are every file of type `output` that GET /history lists for the Job's Result_Nodes, taken from every output list whose entries hold a file name (for example `images` for SaveImage, SaveAnimatedWEBP and SaveVideo, `gifs` for VHS_VideoCombine, `audio` for SaveAudio). Every file of a batch is included and each file is recorded once, ordered first by the Manifest's Result_Nodes and then as GET /history lists them. Each file is recorded with its file name, subfolder, type and media kind (criterion 7).
2. THE Gallery SHALL show the result files of the History's Jobs 50 at a time, with a control that adds the next 50. Files are ordered newest first by the Job's end time (the time the History record gives the Job's final Job_State) and, within one Job, in the order of criterion 1. Each image is a picture scaled to fit a 256 × 256 CSS-pixel tile without cropping, which opens the full-size file when activated. Each video is a player with controls that plays only when the user starts it. Each file of kind other shows as its file name. Every file has a download control, except as criterion 6 states, and a label giving the workflow label, the Job's end time to the second in the browser's time zone, the Job's seed as the exact integer (Requirement 11 criterion 7) and, for a Failed or Cancelled Job, the Job_State.
3. WHILE the Gallery is open, WHEN the Studio_Server records a Job's result files, THE Gallery SHALL show those files in the place criterion 2 gives them within 2 s of the recording, without a page reload.
4. WHEN the user activates a result file's download control, THE Studio_Server SHALL send the file as an attachment under the file name its History record holds, without the subfolder, and encode the name so that quotes, backslashes, semicolons, non-ASCII characters and control characters stay part of that one name and add no header field.
5. THE Studio_Server SHALL fetch a result file only through GET /view, using only the file name, subfolder and type the file's History record holds (a request names the file by a Studio-made id, Requirement 20 criterion 6), and SHALL serve no other file from ComfyUI's folders.
6. IF fetching or showing a result file fails, THEN THE Gallery SHALL show the reason in the file's tile and leave the History record unchanged:
   - for a 404 from GET /view: that the file is no longer in ComfyUI's output folder, with no download control
   - for any other GET /view error status, no answer within 10 s, or no connection to ComfyUI: that the file cannot be fetched now, with that cause and a control that tries again
   - for a file the browser cannot decode or play: that this browser cannot show the file, with the download control kept
7. THE Studio_Server SHALL send each result file with the media type of its extension, ignoring letter case, whatever type GET /view reports:
   - media kind image: image/png (.png), image/jpeg (.jpg, .jpeg), image/webp (.webp) and image/gif (.gif)
   - media kind video: video/mp4 (.mp4), video/webm (.webm) and video/quicktime (.mov)
   - media kind other (any other extension): application/octet-stream, and only as an attachment
8. WHEN the browser requests a result file of up to 4 GiB, whole or as one byte range, THE Studio_Server SHALL answer with exactly the requested bytes and the file's total size, so that video players can seek.
9. IF a Job ends as Succeeded with no result file recorded under criterion 1, THEN THE Studio_Server SHALL keep the Job as Succeeded and record in its History record a Plain_Error, shown as Requirement 15 criterion 6 states, that names each Result_Node and says that none saved a file to ComfyUI's output folder.

### Requirement 17: History

**User Story:** As the user, I want a history of my runs that I can load back into the form, so that I can rerun or vary earlier settings.

#### Acceptance Criteria

1. THE Studio_Server SHALL keep exactly one History record per Job, starting when the Job enters Queued. Each record SHALL hold: the History_Version; the Manifest name and the workflow label; the SHA-256 of the UTF-8 bytes of the Manifest_Printer's canonical JSON of the Manifest, so that reformatting the Manifest file does not change it; the SHA-256 of the UI_Graph file's bytes; the Converter's name and version and the ComfyUI version at the time the Job entered Queued; the Form_State; the seed used, as an exact integer (Requirement 11 criterion 7); the Generate request's request id (Requirement 13 criterion 10); the prompt_id; the submitted prompt, which is absent if the Job ended before submission; the Job_State; the times the Job entered Queued, Running and its final Job_State, in UTC ISO 8601 with milliseconds (for example 2025-01-31T09:05:03.042Z), each absent until the Job enters that state; the result files (Requirement 16 criterion 1); and any Plain_Error. THE Studio_Server SHALL write every Job_State change, time and result file to that Job's record only, and SHALL lose none of them even when several Jobs change Job_State at the same moment.
2. THE Frontend SHALL list the History records newest first by Queued time, 50 at a time: the newest 50 first, then 50 more each time the user asks, until every record is listed. Each record SHALL show the workflow label, the Queued time, the Job_State, the exact seed used and a thumbnail of the first image among its result files, or a placeholder showing that it has none. Each record SHALL offer a Load action. Once the Job has ended (Succeeded, Failed, Cancelled or Lost), the record SHALL also offer a Delete action that asks the user to confirm before deleting.
3. WHEN the user loads a History record whose workflow has a Manifest and is Ready, THE Form SHALL: switch to that workflow; set the seed and its randomize switch as Requirement 11 criterion 9 states; set every other value the record's Form_State holds, except the values criterion 4 refuses, with each Image_Slot showing the Stored_Input its hash names; give each Form value the record does not hold its default; and report differences as Requirement 11 criterion 10 states.
4. IF a loaded History record or Preset holds a Control, Image_Slot, LoRA_Target or Graph_LoRA the Manifest no longer declares, or a value (LoRA_Entries included) that the current type, limits or /object_info choices refuse, or an Image_Slot content whose Stored_Input is no longer in the Studio_Data_Dir, THEN THE Form SHALL: load every other value, keeping the remaining LoRA_Entries in their order; set each declared Control whose value it refused to its default; leave each Image_Slot whose Stored_Input is gone empty; and list every value not loaded with its field, the value and the reason (no longer declared, wrong type or outside the current limits, not among the /object_info choices, or input image missing), keeping the list shown until the user dismisses it or loads again.
5. FOR ALL Form_States the Form accepts, seeds up to 18446744073709551615 included, writing a History record and reading it back SHALL give an equal Form_State (the same fields, value types, values and LoRA_Entry order) and the same value for every other field criterion 1 lists (round trip).
6. WHEN the user confirms the deletion of a History record, THE Studio_Server SHALL remove the record, so that it leaves the list and its result files leave the Gallery. THE Studio_Server SHALL also delete each Stored_Input the record names that no remaining History record or Preset names. It SHALL delete no Stored_Input while any of these exists: a record of a newer History_Version (criterion 8), or a History record or Preset the Studio_Server cannot read (Requirement 19). ComfyUI's input and output files, ComfyUI's own history and every other record and Preset SHALL stay unchanged.
7. IF the user loads a History record whose workflow has no Manifest or is not Ready, THEN THE Form SHALL keep its current workflow and Form_State unchanged and show a Plain_Error naming the workflow and the reason (no Manifest, or the Ready check it fails).
8. WHEN the Studio_Server reads a History record whose History_Version differs from the one it writes, THE Studio_Server SHALL leave the record unchanged. For an older version, it SHALL offer the record for listing and loading like a current record, and each field that version lacks SHALL count as not held (criterion 3). For a newer version, it SHALL leave the record out of the list and report how many records it left out for that reason, and the Frontend SHALL show that count with the list.

### Requirement 18: Presets

**User Story:** As the user, I want to save named settings per workflow and apply them later, so that I can return to setups that work.

#### Acceptance Criteria

1. THE Form SHALL let the user save the current Form_State as a Preset of the current workflow. The Preset SHALL hold every Control value, the seed and its randomize switch, the LoRA_Stacks and the Graph_LoRA switches, and no Image_Slot contents. Its name SHALL hold 1 to 64 Unicode code points and no control character (Unicode general category Cc) after leading and trailing white space (Unicode White_Space) is removed and the rest is normalised to Unicode NFC. The Preset SHALL keep the name in that trimmed, normalised form.
2. IF the chosen name, normalised as criterion 1 states, equals the name of a Preset of the current workflow after Unicode full case folding of both (so that "Portrait" and "PORTRAIT" are one name), including a Preset saved from another browser tab since the Form listed the Presets, THEN THE Form SHALL ask the user to confirm replacing that Preset, naming it, and SHALL replace it with the new Preset, the new spelling of the name included, only when the user confirms, changing no Preset when the user declines.
3. THE Form SHALL list the Presets saved under the current workflow's Manifest name (not those saved under an earlier name of a renamed Manifest, which stay stored), as the Studio_Server holds them when the Form opens and after each save or delete, in ascending Unicode code point order of their case-folded names, and SHALL let the user apply any listed Preset and delete it after confirming a prompt that names it.
4. WHEN the user applies a Preset, THE Form SHALL set every Control value, the seed and its randomize switch, every LoRA_Stack and every Graph_LoRA switch the Preset holds, leave unchanged the Image_Slots and every Control, LoRA_Stack and Graph_LoRA switch the Preset holds no value for (for example a Control added to the Manifest after the Preset was saved), and report the values the Form cannot apply as Requirement 17 criterion 4 states.
5. FOR ALL sequences of Preset saves and deletes for one workflow, reading the Presets back SHALL give each remaining Preset exactly as last saved, including its name, its values and its seed (up to 18446744073709551615). Requests sent concurrently (for example from two browser tabs) SHALL leave the same Presets as handling them one at a time in some order, so that two saves of different names both remain (round trip).
6. IF a Preset save holds a name that breaks the name rules of criterion 1, or would add a 101st Preset to the workflow, THEN THE Studio_Server SHALL save nothing and answer which rule the save breaks.
7. IF the Studio_Server cannot write a workflow's Preset file (for example because the disk is full or read-only), or Requirement 19 criterion 4 skips that file as unparseable, THEN THE Studio_Server SHALL save or delete no Preset of that workflow, leave the file and the Presets it lists as they were before the request, and answer that the change failed, with the file's path and the write or parse error.
8. IF a Preset save or delete is refused under criterion 6 or 7, or the Preset to delete no longer exists (for example because another browser tab deleted it), THEN THE Form SHALL show the reason beside the Preset controls, keep the typed name and every Form value, and list the Presets as the Studio_Server then holds them.

WHEN the Studio_Server reads a Preset file whose format version differs from the one it writes, THE Studio_Server SHALL leave the file unchanged and treat it as Requirement 17 criterion 8 treats a History record of that version (an older file read with each field it lacks counting as not held; the Presets of a newer file left unlisted, with the file's path and version reported in the Frontend and the log), and SHALL save and delete no Preset of a newer file's workflow, answering as Requirement 18 criterion 7 states.

### Requirement 20: Security

**User Story:** As the user, I want Studio reachable only through Vast's authenticated Portal or an SSH tunnel, so that nobody else can use my GPU or see my images.

#### Acceptance Criteria

1. THE Studio_Server SHALL listen only on 127.0.0.1 at the Studio_Port, and SHALL offer no setting that makes the Studio_Server listen on another address.
2. THE Studio_Server SHALL open network connections only to the ComfyUI_API at a loopback address, under the ComfyUI_Client's loopback rules (no proxy, no redirect followed).
3. THE Studio_Server SHALL answer a request, the Live_Socket's WebSocket handshake included, only when its Host header, compared ignoring letter case, names 127.0.0.1, localhost or [::1] with any port or none (an SSH tunnel may use another local port, as `-L 9000:127.0.0.1:18190` does) or matches an entry of STUDIO_ALLOWED_HOSTS, and SHALL answer every other request, one without a Host header included, with HTTP 403, so that a web page whose host name an attacker points at 127.0.0.1 (DNS rebinding) cannot use Studio. STUDIO_ALLOWED_HOSTS is a comma-separated list of host names or IP addresses (the Portal's host names), each with an optional port and no wildcard; an entry with a port matches only that host and port, and an entry without one matches that host with any port or none.
4. IF a POST, PUT, PATCH or DELETE request, or the Live_Socket's WebSocket handshake (Requirement 14 criterion 8), carries an Origin header whose host and port differ from those of the request's Host header (compared ignoring letter case, a missing port equal only to a missing port, and the scheme not compared, because the Portal ends TLS before Studio), THEN THE Studio_Server SHALL answer HTTP 403 and change nothing; a request without an Origin header passes this check.
5. THE Studio_Server SHALL send no CORS header that lets another origin read Studio's answers.
6. THE Studio_Server SHALL name stored inputs, result files, History records and Presets in its HTTP API only by Studio-made ids and content hashes, and SHALL answer HTTP 404 for any other id, so that no request can name a file path.
7. THE Studio_Server SHALL read no credential (HF_TOKEN, CIVITAI_TOKEN, OPEN_BUTTON_TOKEN, WEB_PASSWORD), and SHALL keep request query strings, Cookie headers and Authorization headers (which carry the Portal's token) out of the Studio_Server's log, the History and every message.
8. THE Frontend SHALL load scripts, styles, fonts, images and media only from the Studio_Server's own origin, except previews, which the Frontend shows from blob: or data: URLs made from Live_Socket data.
9. THE Studio_Server SHALL create, change or delete no Job, History record, Preset or Stored_Input, and send ComfyUI no POST /upload/image, /prompt, /queue or /interrupt, in answer to a GET or HEAD request or to a message a browser sends over a Live_Socket (the Conversion_Cache entries that Requirement 3 criterion 1 stores are exempt).
10. THE Studio_Server SHALL send with every answer a Content-Security-Policy header that enforces criterion 8 (scripts, styles, fonts, images and media only from the Studio_Server's own origin, images also from blob: and data: URLs for previews; connections only to the Studio_Server's own host and port, its WebSocket included; no inline script and no eval; `frame-ancestors 'none'`), and the headers `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`.
11. IF a request body is larger than its limit (64 MiB for an image upload, Requirement 7 criterion 5; 1 MiB for any other request), THEN THE Studio_Server SHALL stop reading the body at the limit, change nothing, and answer HTTP 413 with a plain message naming the limit.
12. IF a request body that a route reads as JSON is not valid JSON, THEN THE Studio_Server SHALL change nothing and answer HTTP 400 with a plain message saying where the JSON breaks.
13. THE Studio_Server SHALL send no stack trace and no exception text of its own in any answer, answering an error that no other criterion answers with HTTP 500 and a plain message naming the route, and writing the stack trace to its log only.
14. IF STUDIO_PORT is not a whole number from 1 to 65535, or the Studio_Port is in use, when the Studio_Server starts, THEN THE Studio_Server SHALL log one line naming the port and the cause and exit with a non-zero status (Requirement 21 criterion 12 covers the Studio_Service's side).
15. IF STUDIO_ALLOWED_HOSTS holds an entry that is not a host name or IP address with an optional port (for example `https://host` or `*.trycloudflare.com`), THEN THE Studio_Server SHALL log one line naming the entry and exit with a non-zero status.

### Requirement 21: Service and access

#### Acceptance Criteria

WHEN the Studio_Server receives SIGTERM, THE Studio_Server SHALL stop taking requests, close every Live_Socket and its /ws connection to ComfyUI, let each file write in progress end as Requirement 19 criterion 2 states, abandon each request to ComfyUI in progress (Requirement 13 criteria 6 and 15 settle those Jobs at the next start), and exit with status 0 within 10 s, so that a restart ends before supervisor's 15 s stop wait runs out.
12. IF a start check of Requirement 19 criterion 7 or 9 or Requirement 20 criterion 14 or 15 fails, THEN THE Studio_Server SHALL exit as that criterion states within 10 s of the process start, before supervisor counts the start as good (criterion 10), so that supervisor shows the Studio_Service as FATAL once its start retries are used up, and the Studio_Log holds, for each attempt, the Studio_Server's line naming the cause.
13. WHEN the Studio_Service starts while ComfyUI does not answer at COMFYUI_URL (for example during Vast's first-boot provisioning, which holds ComfyUI back), THE Studio_Server SHALL keep running and serving the Frontend, answer the workflow list with the reason of Requirement 1 criterion 7, and reconnect as Requirement 14 criterion 6 states, without exiting.
14. IF `/var/log/portal` does not exist when `install` registers the Studio_Service (an image older than the Portal), THEN THE Studio_Installer SHALL create the folder, with mode 0755, before it runs `supervisorctl update studio`, so that supervisor can open the Studio_Log.
15. WHEN `install` runs on an Instance whose `studio.conf` is missing while Studio_Home holds a Studio_Venv (a Vast volume reused on a new Instance), THE Studio_Installer SHALL write `studio.conf` and start the Studio_Service, reusing the Studio_Venv where its stamp matches (Requirement 22 criterion 4) and rebuilding it otherwise (Requirement 22 criterion 5).
16. THE Studio_Installer SHALL print the Tunnel_Command with `<host>` and `<port>` taken from Vast's `PUBLIC_IPADDR` and `VAST_TCP_PORT_22` where both are set, as the ai-influencer-pipeline design prints the tunnel of its training UI (Open item 18), and with the placeholders `<host>` and `<port>` otherwise.

IF `/etc/portal.yaml` is missing or lists no entry for the Studio_Port when `install` or `restart` ends, THEN THE Studio_Installer SHALL print that the Instance Portal does not list Studio and that the Tunnel_Command opens it, and, where the user approved P-4 or P-5, point to the Reference_Doc's steps that add Studio to the Portal (Requirement 23 criteria 4 and 5).

### Requirement 24: Frontend and accessibility

**User Story:** As the user, I want a plain web page where every control is labelled and works from the keyboard, so that Studio is quick to use and accessible.

#### Acceptance Criteria

1. THE Studio_Server SHALL be a FastAPI application that serves the Frontend and Studio's HTTP API from one origin.
2. THE Frontend SHALL consist of static HTML, CSS and JavaScript files that the Studio_Server serves as committed, with no build step, bundler or package manager, and with no JavaScript or CSS framework or library from outside the Repo (Requirement 20 criterion 8 keeps out every CDN).
3. THE Frontend SHALL give every control a visible label that assistive technology reads as the control's name.
4. THE Frontend SHALL let the user reach and operate every control with the keyboard alone, in an order that follows the page layout, with a visible focus indicator.
5. THE Frontend SHALL offer a keyboard alternative for every drag action: the file picker for Image_Slots, and move up and move down buttons for LoRA_Entries.
6. THE Frontend SHALL announce each Job_State change and each Plain_Error once through a live region, and SHALL announce there no progress step, step count, executing node, elapsed time or preview.
7. THE Frontend SHALL give each Gallery image and video a text alternative naming the workflow label, the Job's end time and, where the Job has a seed, the Job's seed, as the file's label gives them (Requirement 16 criterion 2); each preview one naming the workflow label, that it previews the Running Job, and the Job's seed where it has one; and each History thumbnail one naming the workflow label and the Queued time.
8. THE Frontend SHALL convey no state by colour alone.
9. THE Frontend SHALL work in the stable releases of Chrome, Firefox and Safari that are current at Studio's release.
10. THE Frontend SHALL meet the success criteria of WCAG 2.2 level AA for the behaviour these requirements name, as a design target: Studio claims no WCAG conformance and seeks no certification, since full validation needs manual testing with assistive technologies and an expert accessibility review.
11. WHEN the Studio_Server refuses a Generate request, THE Form SHALL move keyboard focus to the first field, in page order, that the refusal marks, or, where the refusal marks no field, to its Plain_Error beside Generate.
12. WHILE a confirmation dialog is open (replacing a Preset, deleting a Preset, deleting a History record), THE Frontend SHALL keep keyboard focus inside the dialog and leave the rest of the page inoperable.
13. WHEN a confirmation dialog closes, by its buttons or by Escape (which declines), THE Frontend SHALL return keyboard focus to the control that opened the dialog, or, where the confirmed deletion removed that control, to the next entry of its list, or to the list itself where no entry follows.

THE Frontend SHALL make the searchable lists of Requirement 6 criterion 8 and Requirement 8 criterion 2 follow the WAI-ARIA combobox pattern with a list popup: typing filters the choices, Down Arrow and Up Arrow move through the kept choices, Enter picks the highlighted choice, and Escape closes the list and leaves the selection unchanged.
15. THE Frontend SHALL give every control a pointer target of at least 24 × 24 CSS pixels.
16. THE Frontend SHALL show text at a contrast ratio of at least 4.5:1 against its background, and control boundaries and focus indicators at a contrast ratio of at least 3:1 against the colours next to them.
17. THE Form SHALL show every control and value without horizontal scrolling of the Form at 200% browser zoom in a window 1280 CSS pixels wide, and in a viewport 320 CSS pixels wide, wrapping long values such as file names.
18. WHILE the browser reports `prefers-reduced-motion: reduce`, THE Frontend SHALL show no animation, transition or smooth scrolling.
19. THE Frontend SHALL set the page language to English with `lang="en"` on the `html` element.
20. THE Frontend SHALL tie each field error to the field's control, so that assistive technology reads the error with the control and reports the control as invalid.
21. 22. THE Reference_Doc's checklist SHALL list as hand checks on an Instance (Requirement 27 criteria 11 to 13) what no static test decides: keyboard operation, focus order, dialogs and lists (criteria 4, 5 and 11 to 14); names and announcements with a screen reader (criteria 3, 6, 7 and 20), controls the JavaScript builds included; target size (criterion 15); contrast (criterion 16); zoom and narrow widths (criterion 17); and state shown by more than colour (criterion 8).

### Requirement 27: Acceptance on an Instance

**User Story:** As the user, I want the "done when" scenarios checked on a real Instance, so that Studio is known to work end to end.

Unless a check says otherwise, each runs on an Instance of the stock template with Studio installed by `bash scripts/studio.sh install` and opened through the Tunnel_Command, ComfyUI answering and the Converter present. Each criterion gives its preconditions and the observation that passes; any other outcome fails, and criterion 15 says where the results go.

#### Acceptance Criteria

1. WHILE krea2 is installed (`bash scripts/stock-setup.sh krea2`, then `finish`) and the workflow of `image_krea2_turbo_t2i.json` is Ready, WHEN the user picks that workflow, adds one LoRA_Entry at strength 0.8 with a file the Form lists for its LoRA_Target (for example `lenovo_krea2_3000.safetensors`), turns randomize off, types a seed and presses Generate, THE Gallery SHALL show the Job's image with the typed seed in its label, and the Job's History record SHALL hold a submitted prompt with one Chain_Loader that holds that file at strength 0.8.
2. WHILE the Job of criterion 1 has succeeded and nothing has been installed or changed since, WHEN the user runs `bash scripts/stock-setup.sh restart`, waits until the workflow shows Ready again, loads that Job's History record and presses Generate, THE Studio_Server SHALL submit a prompt equal to the first Job's submitted prompt, both read from their History records and compared as JSON values, except for the Result_Nodes' `filename_prefix` inputs.
3. WHEN the second Job of criterion 2 succeeds, THE Gallery SHALL show an image whose decoded pixels equal those of the first Job's image. This is the user's reproduction check of Requirement 11 criterion 19 (the PNG files differ anyway, because ComfyUI writes the prompt into each). A pixel difference fails the check and is recorded against Open item 6, because Requirement 11 criterion 19 promises equal prompts, not equal pixels.
4. WHILE qwen21-edit is installed, WHEN the user fills the first three Image_Slots of its Form with three different images and presses Generate, THE Studio_Server SHALL submit a prompt that sets the `studio/<name>` references of the three Stored_Inputs, in slot order, on the Image_Loaders that the graph's image inputs 1, 2 and 3 take, with ComfyUI's `input/studio/` folder holding each file byte for byte, and SHALL record the Job as Succeeded with its result shown in the Gallery.
5. WHILE a Job is Running (for example a qwen21 Job at 50 steps), WHEN the user presses the Job's Cancel control, THE Studio_Server SHALL record the Job as Cancelled within 30 s of the press, after which GET /queue at COMFYUI_URL lists the Job's prompt_id neither as running nor as pending.
6. WHILE the Form of the workflow of criterion 1 holds a LoRA_Entry for `lenovo_krea2_3000.safetensors`, applied from a Preset that holds it, WHEN the user moves that file out of ComfyUI's model folders and presses Generate without pressing refresh, THE Studio_Server SHALL record no Job and submit nothing, and the Form SHALL show beside Generate a Plain_Error saying that the LoRA file `lenovo_krea2_3000.safetensors` is not installed, with `bash scripts/stock-setup.sh krea2` as the next step (Requirement 15 criteria 2 and 3). Where ComfyUI still lists the moved file, the check fails and is recorded against Open item 12. The user then moves the file back.
7. WHEN the user lists the Instance's listening TCP sockets (for example with `ss -ltn`) while the Studio_Service runs, THE Studio_Server SHALL be the only listener on the Studio_Port, at 127.0.0.1, with no listener at that port on `0.0.0.0`, `::` or any other address.

9. WHERE the user approved P-4, WHEN the user opens Studio's Portal address on an Instance created with P-4's template settings, THE Portal SHALL ask for its token before it shows Studio, and SHALL show the Frontend once the token is given.
10. WHEN the user runs `bash scripts/studio.sh install` a second time with nothing changed, THE Studio_Installer SHALL report `studio.conf: unchanged` and `service: left running` in its summary, with `supervisorctl pid studio` giving the same process id before and after, and with no file created, changed or deleted below Studio_Home, the Install_Lock apart, or in `/etc/supervisor/conf.d`, as a listing of names, sizes and modification times taken before the run shows.

12. WHEN the user carries out the steps of criterion 1 with VoiceOver in Safari, THE Frontend SHALL let VoiceOver read each control's label as its name, and SHALL announce the Job's Job_State changes and a Plain_Error (for example the refusal of criterion 6) once each, without announcing progress steps.

WHERE the user did not approve P-6, WHEN the user sends, with `curl` on the Instance, the requests that the Reference_Doc's checklist lists, THE Studio_Server SHALL answer HTTP 403 to a request with `Host: evil.example` and to a POST or Live_Socket handshake with `Origin: http://evil.example`, HTTP 413 to a request body over 1 MiB and HTTP 400 to a POST whose body is not valid JSON; send the headers of Requirement 20 criterion 10 with every answer; send a result file as an attachment under its recorded name (Requirement 16 criterion 4); and answer a byte range of a video result with exactly those bytes and the file's total size (Requirement 16 criterion 8).

## Open items

Content from the sources below was rephrased for compliance with licensing restrictions.

1. **Converter on the Instance.** Verified: Vast's ComfyUI image clones SethRobinson's converter into `custom_nodes` at build time, unpinned ([Dockerfile](https://github.com/vast-ai/base-image/blob/main/derivatives/pytorch/derivatives/comfyui/Dockerfile)). POST /workflow/convert takes the UI-format workflow as the request body and answers the API graph with `_meta.title` on every node; an API-format body comes back unchanged; bodies over 1 MB get 413; malformed workflows get 400 and conversion failures 500, both with an `error` text; GET /workflow/convert answers name and version (2.3.0 when checked); nodes inside subgraphs get ids `<outer id>:<inner id>` ([README](https://github.com/SethRobinson/comfyui-workflow-to-api-converter-endpoint), [source](https://github.com/SethRobinson/comfyui-workflow-to-api-converter-endpoint/blob/main/__init__.py)). Not verified: that the image tag the stock template uses today includes the converter; that Instances on a reused volume (whose `custom_nodes` were copied at an earlier first boot) have it; the folder name of that copy, which decides whether P-7's Provisioner run keeps it or clones a second copy beside it (Requirement 23 criterion 20); and whether the converter's repository has release tags for P-7 to pin. Requirement 3 criterion 5 and P-7 cover the gap.
2. **Converter fidelity.** The five Comfy-Org graphs of the first version are built around subgraphs, and the krea2 graphs depend on ComfySwitchNode, PrimitiveBoolean, PrimitiveStringMultiline, TextGenerate (Krea 2 Turbo) and AdvPromptEnhancer (NSFW+ LLM). Whether the converter's output for each graph matches the frontend's Export (API) has to be checked on an Instance before the fixtures are committed.
3. **Portal.** Verified ([base-image README](https://github.com/vast-ai/base-image), [Instance Portal docs](https://docs.vast.ai/guides/instances/connect/instance-portal)): a PORTAL_CONFIG entry reads `hostname:external_port:internal_port:path:name`; the external port has to be opened in the template when the Instance is created; when the two ports differ, Caddy serves the app on the external port with TLS and token authentication; `/etc/portal.yaml` is written at first boot and can be edited later; the Portal's Tunnels page can open a Cloudflare tunnel to any local port. Not verified: whether an edited `portal.yaml` takes effect after `supervisorctl restart caddy` (the README) or only after a reboot (the Portal docs); the layout of `portal.yaml`, which the Reference_Doc has to record from an Instance before P-5 can be built (Requirement 23 criteria 5 and 15); whether the Portal's logs page shows every file in `/var/log/portal` or only its own (Requirement 21 criterion 1); and whether a tunnel opened to Studio's own port skips Caddy's token check, as the docs suggest and Requirement 25 criterion 3 assumes. On Instances created without the port, the SSH tunnel is the fallback.
4. **Host header through the Portal.** The host names Studio sees through Caddy and the Cloudflare tunnels (for STUDIO_ALLOWED_HOSTS, Requirement 20 criterion 3) are to be read on an Instance. The expected forms are the Instance's public address with the mapped port, and `*.trycloudflare.com`.
5. **/ws messages and previews.** Verified in ComfyUI's master branch ([server messages](https://docs.comfy.org/development/comfyui-server/comms_messages), [protocol.py](https://github.com/Comfy-Org/ComfyUI/blob/master/protocol.py), [progress.py](https://github.com/Comfy-Org/ComfyUI/blob/master/comfy_execution/progress.py), [execution.py](https://github.com/Comfy-Org/ComfyUI/blob/master/execution.py)): the JSON messages of Requirement 14 criterion 4, with `progress_state` sent to the submitting client only; binary frames start with a 4-byte type: 1 for a preview (then a 4-byte image type, 1 JPEG or 2 PNG), 3 for progress text, and 4 for a preview with JSON metadata, sent only to clients that announce the `supports_preview_metadata` feature flag; previews are off unless ComfyUI runs with `--preview-method` or the prompt's `extra_data.preview_method` asks for one. Not verified: which of these the Instance's ComfyUI release supports. On a release without `extra_data.preview_method`, previews need a COMFYUI_ARGS change that this spec does not make.
6. **Reproducibility.** Requirement 27 criterion 3 assumes deterministic GPU kernels on one Instance and deterministic prompt refinement under a fixed seed (TextGenerate is on by default in the Krea 2 Turbo graph). ComfyUI restarts between the two runs because its cache would otherwise return the first result. To confirm on an Instance.
7. **wan-i2v graph.** The graph comes from a Civitai zip that is not available here: its file name after extraction, its structure and its two model loaders are to be read on an Instance before its Manifest is written.
8. **Seed bounds.** 18446744073709551615 is KSampler's maximum; the bounds of every other seed input the Manifests bind are to be read from the Instance's /object_info.
9. **Ports.** 18190 (Studio_Port) and 8190 (P-4) are proposals; that both are free on the stock template is to be confirmed. Because Vast opens the external port only when it creates the Instance (Open item 3), P-4's `-p 8190:8190` serves only Instances created after the template holds it, and a running Instance keeps the SSH tunnel (Requirement 23 criterion 13).
10. **Interrupt on older releases.** The ComfyUI_Client's `interrupt` (`scripts/influencer/comfy.py`) notes that older ComfyUI releases ignore the body of POST /interrupt and interrupt whatever runs. Requirement 13 criterion 4 sends the interrupt only right after GET /queue lists the Job's own prompt as running, which narrows, but does not close, the window in which another client's prompt could start and be interrupted instead. Whether the Instance's release honours `prompt_id` is to be read on an Instance.
11. **`COMBO` inputs.** Requirement 4 criterion 4 takes both list forms of /object_info: a list of choices as the type, and `COMBO` with an `options` list. Which form the Instance's ComfyUI sends for each bound input is to be read from its /object_info, and the /object_info fixtures (Requirement 26 criteria 2 and 9) hold what it sends.
12. **New and removed model files.** Requirement 6 criterion 6 (install, then press refresh) and Requirement 27 criterion 6 assume that ComfyUI's /object_info lists a file added to a model folder, and drops a removed one, without a restart. To confirm on an Instance; where a restart is needed, the next step gains `bash scripts/stock-setup.sh restart`.
13. **`execution_success` and the history entry.** Requirement 14 criterion 4 reads GET /queue and then GET /history after `execution_success`, and reads both again while GET /queue lists the prompt. That finds a history entry written after the message, provided ComfyUI takes the prompt off its queue and writes the entry in one step; were there a moment in which neither lists the prompt, Requirement 13 criterion 6 would record a finished Job as Lost. Whether the Instance's release sends the message before it writes the entry, and whether it removes the prompt and writes the entry in one step, is to be read from its source.
14. **Graph switches after conversion.** Requirement 2 criterion 10 gives a Graph_LoRA at most one switch Binding. Whether the Converter keeps a graph switch such as edit-2509's "Enable Lightning LoRA" as one boolean input that the switched nodes link to, or writes the switch's value into each input it feeds, is to be read from the Converted_Graph; in the second case one Binding cannot move the switch.
15. **wan-i2v frame rule.** Requirement 10 criterion 9 assumes that wan-i2v's frame count follows 4n + 1 (5 to 121 frames); the graph's video nodes and their /object_info limits are to be read on an Instance, together with Open item 7.
16. **Byte ranges from /view.** Requirement 16 criterion 8 answers byte ranges. Whether ComfyUI's GET /view answers a Range request with 206 and the range, or always sends the whole file, is to be read on an Instance; in the second case Studio reads past the bytes before the range, which slows seeking in large videos.
17. **System Python.** Requirement 22 criterion 13 builds the Studio_Venv with the Instance's system `python3`. Its version (CPython 3.10 to 3.14 needed; Ubuntu 22.04 ships 3.10 and Ubuntu 24.04 ships 3.12) and the image's Ubuntu release are to be read on an Instance; with another version, STUDIO_PYTHON names an interpreter.
